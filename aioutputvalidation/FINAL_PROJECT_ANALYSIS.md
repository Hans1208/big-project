# (AI Output Validation) JSON Schema 검증 + Contrastive Learning 기반 근거 검증 + MLP 환각 탐지 — 최종 분석

## 핵심 모델 정의

이 프로젝트의 핵심은 AI가 상담 결과를 만든 뒤, 그 결과를 다시 **구조·근거·환각 위험** 관점에서 검증하는 `AI Output Validation` 모델이다. 생성 모델을 대체하는 것이 아니라, 생성된 AI 답변이 사용자에게 전달되기 전 안전성을 확인하는 후단 검증 계층이다.

|검증 계층|무엇을 확인하는가|처리 결과|
|---|---|---|
|JSON Schema 검증|필수 9개 필드, 데이터 형식, 허용값, 사건유형-세부유형 조합|구조 오류는 `high_risk` 후보|
|Contrastive Learning 기반 근거 검증|AI 주장과 상담 전사 문장을 E5 임베딩으로 대조해 가장 가까운 근거를 검색|근거 부족·비지지 주장은 `review_required` 또는 `high_risk` 후보|
|MLP 환각 탐지|Schema 오류, 근거 공백, 근거 부족 비율, 불확실성 누락, 명시적 사실충돌을 결합|환각 가능성과 최종 위험 단계를 계산|

### 최종 동작 흐름

```text
AI 구조화 출력
  → JSON Schema 검증
  → AI 주장 ↔ 전사 근거 문장 Contrastive 검색
  → MLP + 사실충돌·권한/효력 미확인 규칙
  → safe / review_required / high_risk
  → safe는 통과 후보, 나머지는 사람 검토 큐
```

### Round 71 최종 독립 검증 핵심 수치

|항목|결과|의미|
|---|---:|---|
|JSON Schema 통과|90 / 90|최종 평가 출력의 구조 오류 없음|
|3단계 정확 일치|87 / 90 = **96.67%**|안전·검토 필요·고위험 구분 정확도|
|안전/비안전 Precision·Recall·F1|**100% / 100% / 100%**|위험 답변을 safe로 통과시키거나 안전 답변을 위험으로 막은 사례 0건|

**최종 운영 원칙:** `safe`는 자동 통과 후보로 표시하되, `review_required`와 `high_risk`는 반드시 사람 검토 큐로 보낸다. 현재는 자동 차단이 아닌 제한적 운영 후보 단계다.

## 1. 결론

이 모듈은 다음 세 검증 기능을 모두 구현하고, 합성·블라인드 사람 검토 기반 라운드 평가까지 수행했다.

|구성|역할|최신 확인 결과|
|---|---|---|
|JSON Schema 검증|필수 필드·형식·허용값·사건유형/세부유형 조합 차단|Round 66~68 각 30건과 Round 69 90건, 총 180건 생성 출력이 Schema를 통과했고, 자동 테스트 80건이 통과했다.|
|Contrastive 근거 검증|AI 주장과 전사 문장 근거의 유사도 검색·hard-negative 분리|최신 규모 확인 Round 69 기준 E5: Recall@1 0.9333, Recall@3 1.0000, MRR 0.9667.|
|MLP+규칙 환각 탐지|Schema 오류·근거 공백·사실충돌·불확실성을 결합해 3단계 위험 판정|최신 규모 확인 Round 69: 3단계 일치 0.8778, 이진 Precision 1.0000, Recall 0.8500, F1 0.9189.|

환각 판정은 순수 MLP 단독이 아니라, MLP 점수에 JSON Schema 오류와 명시적 사실충돌 규칙을 결합한 안전 우선 파이프라인이다. 규모 확인 Round 69에서 안전 30건은 모두 safe로 일치했고, 고위험 30건은 모두 위험군(`high_risk` 또는 `review_required`)으로 포착했다. 다만 검토 필요 30건 중 9건은 safe로 낮게 분류됐다. 따라서 자동 차단이 아닌 검토 큐·감사 로그를 유지하는 제한적 운영이 적절하다.

## 3. 구조·정책·연동 계약

|구분|최종 원칙|
|---|---|
|입력 계약|AI 구조화 출력은 `schema/ai_analysis.schema.json`을 통과해야 하며, 추가 민감 필드와 사건유형/세부유형 불일치를 차단한다.|
|근거 계약|주장은 전사 문장 청크와 대조한다. 기준 E5는 `query:`/`passage:` 접두어를 사용하고, 근거 순위·top-2 margin·hard-negative를 감사 가능하게 남긴다.|
|위험 계약|`safe`는 근거 있는 요약, `review_required`는 확인이 필요한 유보형 주장, `high_risk`는 Schema 오류·명시적 날짜/금액/확정 사실충돌이다.|
|운영 계약|검증 모듈은 백엔드 API 키를 읽지 않는다. 백엔드는 RAG 결과와 구조화 출력을 주입하고, 검증기는 판정·사유·감사 정보를 반환한다.|
|승격 계약|보정 라운드 수치는 승격 근거로 쓰지 않으며, 새 문장·새 사건의 독립 라운드에서만 판단한다.|

`backend/ai-api`의 `/consult/analyze`에는 검증 결과를 별도 `output_validation` 필드로 반환하는 비차단 연동을 적용했다. 구조화 AI 원본 9개 필드를 검증에만 보존하고, 기존 응답 필드는 유지한다. 검증기 오류는 상담 분석을 실패시키지 않고 `status: "unavailable"`으로 기록한다.

### 3-1. 실제 화면 연동 및 실행 확인 (2026-08-06)

검증 결과가 API 응답에만 머물지 않도록, 상담원·변호사 화면까지 전달하는 연동을 추가했다.

```text
AI API /consult/analyze
  → output_validation 반환
  → Core API가 extracted_json.output_validation으로 저장·전달
  → 프론트엔드가 verification 상태로 변환
  → "AI 응답 검증"에 형식 / 근거 / 환각 위험 표시
```

|화면 표시|실제 검증 값|표시 기준|
|---|---|---|
|형식|`schema_valid`|통과 / 확인 필요 / 검증 미실행|
|근거|`low_support_ratio`, `unsupported_assertions`|근거 확인 / 근거 보강 필요 / 검증 미실행|
|환각 위험|`decision`, `explicit_conflicts`|낮음(`safe`) / 검토 필요(`review_required`) / 높음(`high_risk`)|

과거 분석처럼 검증 결과가 없는 경우에는 통과처럼 보이지 않도록 세 항목 모두 **검증 미실행**으로 표시한다. `review_required`와 `high_risk`는 화면에 표시된 뒤에도 사람 검토 큐로 보내는 기존 정책을 유지한다.

실제 AI API를 테스트 문장으로 두 번 호출해 아래 결과를 확인했다. 두 호출 모두 `status: "available"`, `schema_valid: true`, `decision: "safe"`, `explicit_conflicts: []`, `unsupported_assertions: []`를 반환했다.

|테스트|근거 점수|환각 위험 확률|판정|
|---|---:|---:|---|
|양육비 미지급 상담|0.9186|0.0279 (약 2.79%)|safe|
|상속포기 위임·효력 확인 상담|0.9196|0.0277 (약 2.77%)|safe|

두 번째 사례가 `safe`인 이유는 입력 문장에 권한·효력 확인 표현이 있더라도, 생성된 AI 답변이 이를 확정 사실처럼 단정하지 않았기 때문이다. 이 검증기는 입력의 민감한 단어만으로 위험을 정하는 방식이 아니라, **AI가 실제로 생성한 주장**이 원문을 벗어나거나 과도하게 단정했는지를 평가한다. 현재 모델 모드는 `shadow_evaluation`이므로 결과를 제공·기록하되 자동 차단하지 않는다.

화면에서 실시간 결과를 보려면 프론트엔드(5173), Core API, AI API(기본 8001)가 함께 실행되어야 한다. 프론트엔드와 Core API가 AI API의 기본 주소로 8001을 사용하므로, 로컬에서 AI API를 8000으로만 실행하면 직접 API 검증은 가능해도 화면 분석 흐름에는 연결되지 않는다.

검증 완료: 프론트엔드 production build 성공, Core API `compileJava` 성공.

## 4. 최종 승격 판단 — Round 71

Round 71은 Round 70 보정 사례와 분리한 안전·검토 필요·고위험 각 30건, 총 90건의 최종 독립 검증이다.

|항목|결과|판단|
|---|---:|---|
|3단계 정확 일치|87 / 90 = 96.67%|위험 단계 구분 우수|
|안전/비안전 Precision·Recall·F1|100% / 100% / 100%|위험 답변 안전 통과와 안전 답변 오탐 모두 0건|
|고위험 정확 분류|27 / 30|3건은 review_required로 보수 분류, safe 통과는 0건|
|검토 필요·안전 정확 분류|30 / 30, 30 / 30|모두 일치|
|근거 Recall@1·Recall@3·MRR|100% / 100% / 100%|근거 검색 성능 유지|

**최종 결론: 제한적 운영 후보로 승격 권고.** `safe`는 통과 후보로 표시하고, `review_required`와 `high_risk`는 반드시 사람 검토 큐로 보낸다. 현재 manifest의 `shadow` 모드는 유지하며, 실제 운영 로그를 확인한 뒤에만 자동 처리 범위를 확대한다.

### 제한적 운영 방식

1. JSON Schema 오류 또는 전사에 없는 확정 사실은 `high_risk`로 보낸다.
2. 근거·권한·문서 상태가 불확실하면 `review_required`로 사람 검토 큐에 보낸다.
3. `safe`만 자동 통과 후보이며, 감사 로그와 사람 재검토 경로를 유지한다.
4. 기준 E5는 유지하고, 성능 우위가 검증되지 않은 contrastive 후보 체크포인트는 사용하지 않는다.

## 4. 현재 운영 판단

- 유지: JSON Schema, 기준 `intfloat/multilingual-e5-small`, 현재 출력 위험 분류 정책.
- 조건부 사용: `review_required` 우선 검토 큐와 감사 로그를 유지한 보조 의사결정 도구.
- 미승격: hard-negative 및 multi-positive contrastive 후보 임베더. 독립 Test에서 기준 E5보다 안정적으로 우수하지 않았다.
- 다음 개선: **Round 69 대규모 블라인드 확인(위험 단계별 30건, 총 90건)** 은 완료됐다. Round 68 위험 유형을 문맥·표현으로 확장한 배치이므로, 결과는 규모 확인용으로 해석하고 완전히 새로운 유형만의 독립 일반화 수치로 쓰지 않는다. 안전 30건은 모두 안전으로 일치했지만, 검토 필요 30건 중 9건을 safe로 판단했다. 따라서 현재 정책은 자동 차단 대신 검토 큐를 유지하고, 이 9건 유형을 보정한 뒤 새 독립 검증을 진행해야 한다.

## 7. 보안 및 `.gitignore` 주의사항

`backend/.env`는 열람·수정하지 않았고, 이 PR에도 포함하지 않는다. 환경 파일 제외 규칙은 저장소의 실제 `.gitignore` 구성에서 유지·확인해야 한다. 예시는 다음과 같다.

```gitignore
# Repository root only
backend/.env
backend/.env.*
!backend/.env.example
**/.env
**/.env.*
!**/.env.example
```

API 키, 실제 상담 원문, 주민등록번호·연락처·녹음 파일은 GitHub에 올리지 않는다. 현재 검증 데이터는 합성 `SYN-*` 식별자를 사용하지만, 실제 데이터를 추가할 경우 위 제외 경로로 분리한다.
